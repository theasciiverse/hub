# Catalog format

Two layers, the way Homebrew and the AUR do it:

1. **Manifests**: one hand-written TOML file per title,
   `hub/catalog/<id>.toml`, reviewed by PR, with its store page beside it
   in `hub/catalog/<id>.md` (see "Page" below).
2. **`catalog.json`**: generated by `hub`'s build from every manifest plus
   release data, published to Pages, fetched by `av` and by the website.
   Never edited by hand.

A single hand-maintained `catalog.json` would rot as soon as a download URL
changed; this split keeps the human-edited part small and stable.

## Manifest (`schema_version = 1`)

```toml
schema_version = 1
id = "solitty"                 # lowercase, [a-z0-9-], same as the file name
kind = "game"                  # game | program | movie | mud | adventure (a text adventure story) | art (demos, effects and ANSI/ASCII art)
title = "Solitty"
description = "Ncurses-based Klondike solitaire, packaged for the Asciiverse catalog"
license = "MIT"                # SPDX id, or "Proprietary" for closed titles
repo = "theasciiverse/solitty" # optional: closed titles may have no public repo
topics = ["terminal", "ncurses", "solitaire"]
genre = "card"                 # games only
funding = "https://..."        # optional, proposed: the developer's own donation link
provenance = "Murilo Pereira wrote solitty, an ncurses Klondike, between 2010 and 2018."
                               # a short note on history and provenance only: who made
                               # it, when, where, how it came to be; one or two plain
                               # sentences, shown as "Where it comes from" on the store
                               # page and in av. No copyright or licence, no changes,
                               # fixes, builds, versions or updates
changes = "PATCHES.md"         # optional: path in `repo` listing what Asciiverse changed
                               # (for a story, its README with the provenance)
collection = "nbsdgames"       # optional: the collection the game comes from, a key
                               # in collections.toml (see "Collections" below)

[developer]                    # who ships this build
name = "Asciiverse"
url = "https://asciiverse.sh"

[upstream]                     # the original, when it is a port or a package;
                               # url is the original project's own home or source,
                               # where one exists, not an encyclopedia page
name = "Murilo Pereira"
url = "http://murilopereira.com"

[exec]
game = "solitty"               # binary inside the install dir; av adds .exe on Windows
args = []                      # optional: arguments av passes at launch, e.g. ["-f"]

[min_terminal]                 # the smallest size the title is playable at
cols = 57
rows = 28

[requires]
utf8 = true
color = "basic"                # basic | 256 | truecolor
mouse = true
gamepad = false                # optional: true when it also plays with a gamepad
glyphs = []                    # optional: "braille", "octants", ... so av can warn about fonts

system_deps = ["libncursesw6"] # free-text hint; av warns, never installs

[media]
cast = "resources/solitty.cast" # path in `repo`, or a full https URL
thumbnail_at = 5.0              # seconds into the cast for the still frame
# crop = { follow = "player" }  # proposed: only for casts recorded bigger than
#                               # 100x30 (RECORDING.md); hub's build cuts a 100x30
#                               # window, centred or following the player

[release]
source = "github"              # github | direct
```

### `release.source = "github"`

The build reads the latest GitHub Release of `repo`. The release must have:

- one archive per target, named `<id>-<target-triple>.tar.gz` (Linux, macOS)
  or `<id>-<target-triple>.zip` (Windows),
- a `SHA256SUMS` file listing those archives.

Version, URLs, sizes, checksums and release notes are all taken from the
release. The repo (or at least its releases) must be publicly readable:
GitHub requires authentication to download assets from a private repo.

### `release.source = "direct"`

For closed-source titles, or anything not released on GitHub. Version and
files are written into the manifest, so **every update is a PR to `hub`**:

```toml
[release]
source = "direct"
version = "1.2.0"
notes_url = "https://example.com/mygame/changelog"   # optional

[release.platforms.x86_64-unknown-linux-gnu]
url = "https://example.com/mygame/mygame-1.2.0-x86_64-unknown-linux-gnu.tar.gz"
sha256 = "..."

[release.platforms.aarch64-apple-darwin]
url = "..."
sha256 = "..."
```

Any public HTTPS URL works. `hub`'s build downloads each file once and fails
if its checksum does not match the manifest.

### MUDs (`kind = "mud"`)

A MUD is a world on someone else's server, so there is nothing to download:
no `[exec]`, `[release]`, `[requires]` or targets. av's Connect opens it in
Lera, the Asciiverse MUD client (`programs/lera`), or in `telnet` when Lera is
not installed. Lera reads the same entries from av's cached `catalog.json`
for its own world list.

```toml
schema_version = 1
id = "aardwolf"
kind = "mud"
title = "Aardwolf"
description = "Huge questing MUD, friendly to newcomers and known for screen-reader support"
since = 1996                   # the year the world opened
topics = ["fantasy", "questing", "gmcp"]
website = "https://www.aardwolf.com"

[connect]
host = "aardmud.org"
port = 4000                    # plain telnet
# tls_port = 0                 # optional: a TLS port; Lera uses it when present

[media]                        # optional: a cast recorded in Lera, as for any title
cast = "https://..."
thumbnail_at = 5.0
```

The page (`<id>.md`) works as for any title: what the world is, how to
start, and its history.

### Collections

Some upstream projects are collections of games (New BSD Games, BSD Games,
gg, cgames). Each game in one is its own title, with its own preview and
page, and names its collection with `collection`. The collection itself is
described once, in `hub/catalog/collections.toml`:

```toml
[nbsdgames]
name = "New BSD Games"
url = "https://github.com/abakh/nbsdgames"   # the collection's own home
description = "Twenty-two small curses games by abakh and contributors, public domain"
```

av and the website show "Part of New BSD Games" on each of its titles and
list the others. All of a collection's games usually come from one repo and
one release, with one archive per game (`<id>-<target>.tar.gz`). Ids follow
the game, with the collection's short prefix only where the plain id is
taken or would shadow a common command (`nbsd-sos`).

### Targets

Rust triples, e.g. `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl`,
`aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`,
`x86_64-pc-windows-msvc`. Prefer `musl` static builds for Rust titles on
Linux (no glibc version skew across distros). C/C++ titles may link system
libraries dynamically and declare them in `system_deps`.

## Page (`<id>.md`)

Every title has a page file next to its manifest: `catalog/solitty.toml`
and `catalog/solitty.md`. It is the body of the title's store page, shown
in `av`'s detail pane and on the website. Decided 2026-10-10; `solitty.md`
is the worked example.

The manifest's one-line `description` stays: it is the summary used in
lists, search results and link previews. The page is the full text.

**Format:** a small subset of CommonMark, chosen because it reads well in
a terminal as well as in a browser:

| Allowed | Not allowed |
|---|---|
| paragraphs | `#` headings (the page title comes from the manifest) |
| `##` and `###` headings | images (the `.cast` is the visual) |
| bullet and numbered lists, one level of nesting | raw HTML |
| `**bold**`, `*italic*`, `` `inline code` `` | tables |
| links, `https://` or `http://` only | fenced or indented code blocks |

`hub`'s build rejects a page that uses anything in the right column, so
`av` and the website only ever have to render the left one. Hard line
breaks inside a paragraph are ignored, as in any Markdown.

**Conventions**, not enforced: open with a short paragraph or two saying
what the title is and how it plays, then any of these sections in this
order:

- `## Controls`: strongly recommended; every key the player needs
- `## Options`: command-line flags, if any
- `## History`: for ports, restorations and classics, the original and
  what this edition changes
- `## Credits`: original authors, this edition, license

Keep it to a few hundred words so it fits `av`'s detail pane with little
scrolling. Leave out which upstream version, release or commit this
edition is built from (the version field shows that) and layout details
such as centring in the terminal or following a resize, and anything
that hedges about rights (folklore being public domain, art being new):
state the licence and the credits it requires, nothing more. Patch notes do
not belong here either; they come from release notes
and `CHANGELOG` (see `../../av/CLAUDE.md`, "Detail pane content").

### Not yet specified

- How movies launch (depends on movie playback design).
- The "OLD!" and "NEW!" banners: manual storefront curation, no field yet.

## Generated `catalog.json`

Every manifest merged with build-time fields. `page` is the raw Markdown
from `<id>.md`, unrendered, so each consumer renders it its own way:

```json
{
  "schema_version": 1,
  "catalog_generated_at": "2026-10-06T12:00:00Z",
  "collections": {
    "nbsdgames": { "name": "New BSD Games", "url": "...", "description": "..." }
  },
  "titles": {
    "solitty": {
      "...every manifest field...": "...",
      "page": "Klondike solitaire in your terminal: ...",
      "version": "1.4.1",
      "updated_at": "2026-10-06T10:00:00Z",
      "cast_url": "https://...",
      "platforms": {
        "x86_64-unknown-linux-gnu": { "url": "...", "sha256": "...", "size": 123456 }
      }
    }
  }
}
```

One file for the whole catalog to start with. Split it (by kind, or an index
plus per-title files) only once size actually becomes a problem.

## Build schedule

A scheduled GitHub Action in `hub` regenerates `catalog.json` every 6 hours,
plus on every merge to `hub`'s main branch. Scheduled polling avoids needing
`repository_dispatch` (and a token) in every title's repo.
